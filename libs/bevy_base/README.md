# Bevy Base (DLL-Friendly ECS)

Welcome to a specialized fork of foundational Bevy crates (version 0.19.0). This repository provides a slightly modified version of Bevy's ECS designed specifically to facilitate dynamic linking and cross-DLL plugin architectures.

## Drop-in Replacement

This `bevy_base` is designed primarily as a direct, drop-in replacement for the fundamental `bevy_ecs`. We have found that the vast majority of third-party crates depending on `bevy_ecs` can be recompiled against this fork and work perfectly correctly. For this reason, **the crate name remains exactly `bevy_ecs`** rather than being renamed. This allows you to smoothly patch it into existing ecosystems via `[patch.crates-io]` without needing to rewrite downstream dependencies.

## Motivation: Cross-DLL Type Identity

In standard Rust, `std::any::TypeId` is generated by the compiler and can vary depending on compilation conditions. When passing ECS components (like `World` or `App`) across DLL boundaries, mismatched `TypeId`s can cause plugins to fail to recognize components spawned by the host or other plugins.

If we strictly relied on Rust's native `TypeId`, developers would have to guarantee that all crates (host and all DLL mods) are compiled under the exact same `cargo build` conditions, using the exact same compiler version and flags, to ensure `TypeId` alignment. 

## Our Solution: Name-Based StableTypeId

To make cross-DLL development more convenient and resilient, we have modified `bevy_ecs` to use an internal, deterministic `StableTypeId`. Instead of relying on the compiler's memory state, `StableTypeId` calculates a hash based directly on the fully qualified name of the type.

This ensures that a `Component` or `ScheduleLabel` retains the exact same identity regardless of whether it was compiled into the host executable or a hot-swapped DLL plugin.

*(Note: We also disabled the `reflect` feature by default in this fork to simplify the core dependency graph for DLL distribution.)*

## ⚠️ Important Note on Safety and Consistency

While hashing by name elegantly solves the identity problem across DLLs, **it does not guarantee structural safety or memory consistency.** 

If a component's internal fields or memory layout change between the host and the DLL (for example, due to mismatched dependency versions), the name-based hash will still match, but passing the data will lead to undefined behavior (e.g., memory corruption or segfaults). 

Ensuring ABI (Application Binary Interface) compatibility and memory layout consistency across binary boundaries is entirely the responsibility of the developer. This is a fundamental requirement of working with native C-ABI DLL modules. 

If you are just getting started with Rust or prefer to rely on the compiler's strict safety guarantees, we warmly recommend sticking to standard static linking (compiling everything into a single executable). But if you are building an advanced, modular engine architecture and are comfortable managing these ABI contracts yourself, this fork is built for you!
